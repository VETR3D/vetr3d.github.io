Abstract

Visual agents for symbolic graphics reasoning depend on executable world representations, yet continued improvement remains bottlenecked by ambiguous supervision from final renders. While recent agentic systems refine scenes through repeated interaction, they lack mechanisms to recursively extract actionable evidence from execution traces—overlooking which proposed symbolic edits survived, disappeared, or interfered during program execution.

To address this, we propose VETR (Verified Execution Trajectories for Refinement), a framework that enables recursive self-improvement over executable world representations for robust symbolic graphics reasoning. Given an initial generation trajectory, VETR maintains complete execution records as an authoritative world state and introduces an execution refiner that recursively distills observed writes and their realized consequences into bounded program updates. Without additional language-model calls for repair, the refiner checks that selected effects are realized while captured surrounding state is preserved; the visual verifier then assesses goal relevance.

Evaluations on BlenderGym and BlenderBench compare visual editing across model backbones. Matched BlenderBench ablations show that execution refinement improves aggregate errors for GPT-5.6-luna and Qwen3.8-27B, while repeated diagnostic runs and fixed-proposal controls isolate the benefits of trace-derived updates and compatible resource bindings.

Refinement Through Execution Evidence

VETR separates realizing a proposed edit from judging its visual quality. The execution refiner validates the change; the visual verifier evaluates the goal.

1 Recover

Extract witnessed values that were overwritten or failed to survive execution. Treat them as candidate updates.

2 Compile

Resolve conflicting resource bindings with local copies, while retaining compatible sharing.

3 Validate

Check that supported edits take effect and captured surrounding state is preserved before visual assessment.

0 additional LLM calls for repair construction. Runtime validation uses at most six additional executions per proposal; model weights remain fixed.
